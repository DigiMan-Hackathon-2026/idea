# DigiMan UX 원칙 v0.1

작성일: 2026-11-21 · 상태: 구현 기준

이 문서는 DigiMan의 사용자 화면·상호작용·문구를 만들거나 검수할 때 항상 적용하는 기준이다. 토스의 공개 UX 자료에서 원칙을 참고하되 토스의 브랜드, 색상, 컴포넌트 외형을 복제하지 않는다. DigiMan의 대상 사용자, 일본어·한국어 이중 언어, 장소 정보의 불확실성과 익명 진행 기록에 맞게 재해석한다.

## 참고한 공식 자료

- [토스의 8가지 라이팅 원칙들](https://toss.tech/article/8-writing-principles-of-toss): 명확함·간결함·친근함·존중·공감, 다음 화면을 예상할 수 있는 힌트, 의미 없는 표현 제거, 쉬운 말, 강요하지 않는 문구를 기준으로 삼는다.
- [모티베이션을 디자인하기](https://toss.tech/article/design-motivation): 한 화면에서 한 가지 핵심 메시지에 집중하는 `One thing per one page` 원칙을 화면 검수에 사용한다.
- [좋은 에러 메시지를 만드는 6가지 원칙](https://toss.tech/article/21021): 오류를 먼저 예방하고, 사용자가 이해할 수 있는 이유와 최소 비용의 해결 행동을 제공하며, 부정적인 감정을 줄인다.
- [디자인 시스템 다시 생각해보기](https://toss.tech/article/44097): 반복되는 결정은 공통 컴포넌트와 토큰으로 일관되게 제공하되 실제 제품 문제를 해결할 수 있는 유연성을 유지한다.

## DigiMan 핵심 원칙

### 한 화면에는 한 가지 핵심 행동만 둔다

- 화면마다 사용자가 지금 이해하고 수행할 가장 중요한 행동 하나를 정한다.
- 주요 행동은 시각적으로 가장 강한 버튼 하나로 표현한다.
- 보조 행동은 링크나 약한 버튼으로 분리하고 주요 행동과 경쟁시키지 않는다.
- 설명이 길어지면 다음 단계에 필요한 내용만 남기고 나머지는 접거나 다음 화면으로 옮긴다.

### 버튼을 누른 다음 일을 예측할 수 있게 쓴다

- `확인`, `다음`, `계속`만 단독으로 쓰지 않는다.
- `퀘스트 찾기`, `기록을 만들고 시작하기`, `주소 복사`처럼 동사와 결과를 함께 쓴다.
- 버튼 장식용 화살표는 쓰지 않는다. 이동 방향보다 행동 결과를 문구로 설명한다.
- 저장·삭제·전송 여부와 외부 이동 여부를 누르기 전에 알 수 있게 한다.

### 짧고 말하듯 쉬운 문장을 쓴다

- 한 문장에는 가능한 한 메시지 하나만 담는다.
- 제품·개발 용어 대신 사용자가 일상에서 쓰는 말을 사용한다.
- 화면 안에서 같은 사실을 반복하지 않는다.
- 정보 전달에 영향이 없는 수식어와 영어 장식 문구를 제거한다.
- 한국어와 일본어는 직역하지 않고 각 언어에서 자연스럽게 소리 내어 읽히는지 확인한다.

### 사용자의 선택권과 신뢰를 지킨다

- 손해·불안·마감 압박으로 행동을 강요하지 않는다.
- demo, 브라우저 저장, 외부 전송 여부, 가격·장소 정보의 확인 상태를 행동 전에 밝힌다.
- 실제 방문이나 출석을 확인하지 않았는데 확인한 것처럼 표현하지 않는다.
- 위험하거나 되돌릴 수 없는 행동은 결과를 먼저 설명하고 명시적으로 확인받는다.

### 오류보다 예방과 복구를 먼저 설계한다

- 선택할 수 없는 항목은 처음부터 노출하지 않거나 선택 전에 조건을 설명한다.
- 오류가 발생하면 `무슨 일이 생겼는지`, `사용자가 할 수 있는 것`, `바로 실행할 행동`을 제공한다.
- 해결 행동은 가능한 한 같은 화면에서 한 번에 실행할 수 있게 한다.
- 복구 가능한 오류에는 다시 시도 또는 안전한 대체 경로를 제공한다.
- 오류의 심각도보다 과한 빨간색, 경고 표현, 모달을 사용하지 않는다.

### 행동 결과를 즉시 보여준다

- 비동기 행동 중에는 중복 실행을 막고 진행 중임을 문구로 알린다.
- 저장·복사·완료 결과는 해당 행동 가까이에서 즉시 확인할 수 있게 한다.
- 성공 여부가 불명확하면 성공했다고 추측하지 않고 서버나 저장 상태를 다시 확인한다.
- 완료 순간에는 사용자가 해낸 행동을 인정하되 실제 방문·출석을 과장하지 않는다.

### 반복 규칙은 시스템으로 유지한다

- 색상, 간격, 버튼, 입력, 모달, 오류 상태는 공통 토큰과 컴포넌트를 우선 사용한다.
- 한국어와 일본어는 같은 정보 구조·행동·오류 복구를 제공한다.
- 새 예외가 필요하면 화면에서 임시로 우회하지 않고 공통 컴포넌트가 수용할지 먼저 판단한다.
- 원칙이 제품 문제 해결을 방해하면 근거와 검증 결과를 기록하고 원칙을 갱신한다.

## 화면 검수 체크리스트

- [ ] 이 화면의 핵심 메시지와 주요 행동을 각각 한 문장으로 설명할 수 있다.
- [ ] 가장 강한 버튼은 하나이며, 버튼 문구로 다음 결과를 예상할 수 있다.
- [ ] 사용자가 지금 알 필요 없는 설명과 반복 문구가 없다.
- [ ] demo·저장·삭제·외부 전송·비용 조건을 숨기지 않는다.
- [ ] 오류 상태에서 사용자가 바로 실행할 수 있는 복구 행동이 있다.
- [ ] 로딩·성공·실패·빈 결과를 행동 가까이에서 확인할 수 있다.
- [ ] 한국어·일본어가 같은 의미와 행동을 제공하며 두 언어 모두 자연스럽다.
- [ ] 360px, 키보드, reduced motion과 screen reader 기준을 해치지 않는다.

## 적용 범위

이 원칙은 랜딩, 탐색, 상세, 진행, 완료, 기록, 운영 화면과 모든 오류·로딩·빈 상태에 적용한다. API 오류 code와 내부 기술 용어는 로그와 계약에 유지할 수 있지만 사용자 화면에는 그대로 노출하지 않는다.
