# DigiMan 결정 큐

최종 갱신: 2026-11-21 · 상태: 실행 전 우선순위

이 문서는 아직 확정되지 않은 제품·기술·운영 선택을 의존 순서대로 관리한다. [현재 구현 준비도](READINESS_STATUS.md)는 영역별 상태를 보여 주고, 이 큐는 누가 어떤 근거로 언제 결정을 내려야 하는지와 미확정일 때의 안전한 기본 행동을 정의한다.

## 상태

| 상태 | 의미 |
| --- | --- |
| `ready` | 필요한 근거가 있어 결정 회의를 열 수 있음 |
| `collecting` | 사용자·팀·공식 source 근거 수집 중 |
| `waiting` | 외부 답변·권한·계정 대기 |
| `blocked` | 선행 결정 전에는 판단하면 안 됨 |
| `decided` | 선택·근거·영향 문서와 commit이 있음 |
| `deferred` | 근거 부족으로 범위를 축소하고 정한 시점까지 보류 |

시간이 없다는 이유로 `waiting`·`blocked`를 암묵적 yes로 바꾸지 않는다.

## 의존 순서

```text
D01 행사 규칙 ───────────────► D07 F0 버전·scaffold ─► D09 외부 계정·배포
      │                                      │
      └─ 인터뷰·콘텐츠 허용 범위             └─► D10 OIDC·운영 환경

D02 일본어 검수자 ─► D03 인터뷰 실행 ─► D04 타깃·문제
                                          │
                                          └─► D05 첫 지역 ─► D06 첫 quest

D06 첫 quest + D09 외부 환경 + D11 복구·보존 + D12 release 근거
                                          │
                                          └─► 공개 운영 여부
```

가상 demo는 D04~D06 전에도 구조 검수에 사용할 수 있지만 실제 사용자 가치나 업체 이용 가능 근거를 대신하지 않는다.

## 지금 실행할 순서

### 외부 연락이 필요한 일

1. D01의 [주최 측 질문](EVENT_RULES_CHECKLIST.md)을 보낸다.
2. D02의 일본어 검수자에게 모집·동의·자극물 P0 범위와 가능한 날짜를 확인한다.
3. 검수 뒤 D03 [모집 문안](../research/RECRUITMENT_MESSAGES.md)을 게시한다.
4. 팀원에게 D08 역할 묶음·기술 경험·가용 시간을 확인한다.

### 저장소에서 근거가 들어올 때 할 일

1. 공식 규칙 답변을 D01 결정 issue와 규칙 확인서에 기록한다.
2. 일본어 검수 결과를 source section·상태·commit으로 반영한다.
3. 인터뷰마다 익명 기록을 추가하고 3개 시점에 합성한다.
4. D04 결정 뒤에만 실제 지역 후보 점수를 비교한다.
5. D06 register 통과 전 실제 quest를 API seed·demo 발표에 사용하지 않는다.

## 결정 기록 최소 항목

결정할 때 repository의 `제품·기술 결정` issue form을 사용하고 다음을 남긴다.

```markdown
# Dxx 결정 제목

- 상태: decided / deferred
- 결정일·시간대:
- 결정 owner·reviewer 역할:
- 근거 commit·공식 source:
- 선택:
- 선택하지 않은 대안:
- 반대 증거·남은 불확실성:
- 영향받는 사용자·API·DB·운영·비용:
- 되돌림·이행:
- 무효화 조건과 재검토 시점:
```

사람 이름과 외부 계정 ID·secret은 넣지 않는다.

## 근거 품질

| 결정 유형 | 강한 근거 | 단독으로 부족한 근거 |
| --- | --- | --- |
| 사용자 문제 | 최근 실제 사건·행동·대체 선택 | 아이디어 호감·“쓸 것 같다” |
| 지역·quest | 독립 사례 + 현장·공식 사실 확인 | 가상 자극물 선호·검색 인기 |
| 행사 범위 | 공식 공지·담당자 답변 | 안내 이미지 기억·다른 행사 관행 |
| package | 공식 지원 문서·lockfile clean test | latest 설치 성공 한 번 |
| 외부 서비스 | 공식 plan·region·실제 계정 설정·측정 | marketing 문구·과거 가격 |
| backup | 별도 DB 복구·cleanup 증거 | backup 기능이 있다는 문서 |
| 일본어 | 모어 화자 + 실제 화면 문맥 | 자동 번역·작성자 판단 |

공식 문서도 조사일 이후 바뀔 수 있으므로 계정 생성·release 직전에 다시 확인한다.

## 결정이 상충할 때

우선순위는 다음과 같다.

1. 행사 공식 규칙과 법적·권리 조건
2. 사용자 안전·개인정보·권한·데이터 정합성
3. 최근 실제 사용자 사건과 반대 증거
4. 검수 가능한 핵심 세로 흐름
5. 개발 속도·시연 편의

빠른 demo를 위해 개인정보·권리·권한 통제를 낮추지 않는다. 사용자 가설이 반대 증거와 충돌하면 기존 스펙보다 새 근거를 검토하되 변경 영향과 이력을 유지한다.

## 정기 갱신

- 새 외부 답변·인터뷰 합성·비용·호환성 결과가 생긴 기능 commit에서 갱신한다.
- `decided` 항목은 표에서 지우지 않고 결정 문서·commit 링크로 바꾼다.
- 마감이 지나도 근거가 없으면 `decided`가 아니라 `deferred`와 안전한 축소 범위를 기록한다.
- 준비도 표의 상태와 다르면 같은 commit에서 맞춘다.

현재 가장 높은 leverage는 D01·D02·D03이다. D07 이후 기술 결정을 더 세밀하게 하는 것보다 먼저 공식 작업 범위와 사용자 사례를 확보해야 한다.
